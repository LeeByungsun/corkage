# Agents and Skills

## 핵심 결론

이 프로젝트는 처음부터 `executor` 중심으로 가는 구조가 아닙니다.

지금은 `researcher + architect + planner + verifier + writer` 조합이 핵심입니다.

즉, `만드는 단계`보다 `가능한지 검증하고 범위를 자르는 단계`가 먼저입니다.

## 1. 현재 단계에서 필요한 에이전트

### researcher

역할:

- 네이버 공식 문서 확인
- API 권한, 인증 방식, 사용 제한 확인
- 검색 API와 지도 API의 역할 구분

이 프로젝트에서 필요한 이유:

- 네이버 지도와 네이버 검색 API가 서로 다른 성격이라 사전 확인이 꼭 필요함
- `콜키지 가능` 데이터가 공식 API에서 오는지 아닌지 먼저 분리해야 함

산출물:

- API 후보 목록
- 사용 가능/보류/제외 판단
- 테스트 체크리스트

### architect

역할:

- 데이터 흐름 설계
- 브라우저/서버 역할 분리
- 외부 API와 내부 저장 구조 정의

이 프로젝트에서 필요한 이유:

- 지도 표시와 콜키지 데이터 저장을 분리해서 봐야 함
- MVP에서 어디까지 네이버 API에 기대고 어디부터 자체 DB를 둘지 결정해야 함

산출물:

- 시스템 흐름도
- MVP 데이터 모델 초안
- API 경계 정의

### planner

역할:

- 검증 작업 순서 설계
- 우선순위 정의
- 산출물 목록 정리

이 프로젝트에서 필요한 이유:

- 지금은 개발보다 검증 순서가 더 중요함
- API 테스트를 무작정 하면 문서만 늘고 결론이 안 남을 수 있음

산출물:

- 주간 작업 순서
- 테스트 단계표
- 완료 기준

### designer

역할:

- 사용자 흐름 설계
- 지도 UX와 리스트 UX 분리
- 필터와 상세정보 구조 설계

이 프로젝트에서 필요한 이유:

- 지도 서비스는 데이터보다 탐색 흐름이 먼저 망가지기 쉬움
- 검색, 필터, 상세 진입 흐름을 초기에 잡아야 함

산출물:

- 사용자 플로우
- 정보 구조
- 핵심 화면 목록

### verifier

역할:

- 가설 검증
- 테스트 결과 판정
- 문서와 실제 결과 대조

이 프로젝트에서 필요한 이유:

- `된다더라` 수준이 아니라 실제 MVP 가능 여부를 판단해야 함
- 인증, 호출 제한, 응답 필드, UX 한계 등을 확인해야 함

산출물:

- 테스트 결과표
- 리스크 목록
- 진행 가능 / 보류 판단

### writer

역할:

- 결정사항 문서화
- README, 계획서, 결정 로그 정리

이 프로젝트에서 필요한 이유:

- 지금 단계는 코드보다 의사결정 기록이 중요함

산출물:

- 계획 문서
- 결정 로그
- 후속 구현 가이드

## 2. 구현 단계에 들어가면 추가할 에이전트

### executor

실제 기능 구현 담당.

### debugger

API 연결 오류, 인증 오류, CORS, 지도 렌더링 문제 대응.

### test-engineer

핵심 API 래퍼, 데이터 정규화, 필터 로직 검증.

### code-reviewer

구현이 시작된 뒤 품질 검토.

### security-review

이건 에이전트가 아니라 스킬이지만, 키 관리가 들어가면 반드시 고려해야 합니다.

## 3. 현재 단계에서 필요한 스킬

### plan

언제 쓰나:

- 작업 순서를 정리할 때
- 기획 문서의 뼈대를 먼저 만들 때

이 프로젝트 적합성:

- 지금 단계의 기본 스킬

### ralplan

언제 쓰나:

- API 선택지 비교가 필요할 때
- 구현 전 PRD와 테스트 스펙 수준의 정리가 필요할 때

이 프로젝트 적합성:

- 가장 잘 맞는 상위 기획 스킬 중 하나

### analyze

언제 쓰나:

- 기존 코드가 생긴 뒤 구조를 파악할 때
- API 테스트 결과나 설계 초안을 깊게 뜯어볼 때

이 프로젝트 적합성:

- 초기 문서나 테스트 결과를 근거 중심으로 분석할 때 유용

### note

언제 쓰나:

- 짧은 결정사항을 바로 남길 때

이 프로젝트 적합성:

- API별 메모와 의사결정 로그에 유용

### wiki

언제 쓰나:

- 장기 프로젝트 지식을 축적할 때

이 프로젝트 적합성:

- 식당 데이터 정책, API 정책, 운영 규칙 축적용으로 좋음

## 4. 조건부로 좋은 스킬

### deep-interview

사용 시점:

- 서비스 범위가 너무 넓을 때
- `서울만 할지`, `예약/리뷰까지 넣을지`, `제보형으로 열지` 같은 결정이 모호할 때

### security-review

사용 시점:

- 서버 키 보관
- API 프록시
- 관리자 화면
- 제보/로그인 기능 추가

### code-review

사용 시점:

- 실제 코드가 생긴 뒤

## 5. 추천 운영 순서

1. `plan`
   - 이번 주 검증 범위 정리
2. `researcher`
   - 공식 문서 확인
3. `architect`
   - 데이터 흐름 초안 작성
4. `designer`
   - 핵심 화면/탐색 흐름 정리
5. `verifier`
   - 테스트 결과 판정
6. `writer`
   - 문서 확정

## 6. 지금 당장 불필요한 것

아래는 아직 우선순위가 낮습니다.

- 대규모 구현 에이전트 운용
- 복잡한 병렬 개발
- 세부 컴포넌트 설계
- 성능 최적화
- 배포 자동화

## 7. 가장 현실적인 다음 액션

다음 단계는 아래입니다.

1. 사용할 네이버 API 후보를 1차 확정
2. API별 테스트 체크리스트 문서 작성
3. 콜키지 데이터 스키마 초안 작성
4. MVP 화면 4~5개 수준으로 축소
5. 그 다음에만 실제 앱 초기화
