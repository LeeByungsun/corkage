# Naver Web Crawling Feasibility for Corkage

작성일: 2026-05-18

## 한줄 결론

`네이버 공식 API만으로 콜키지용 상세 플레이스 데이터를 안정적으로 확보하기는 어렵고, 네이버 웹/내부 API 크롤링을 서비스 핵심 수집 경로로 잡는 것은 정책·robots·반자동화·스키마 드리프트 리스크가 커서 비추천`입니다.

## 범위

이 문서는 `콜키지 가능한 식당` 서비스를 만들기 위해 네이버 데이터를 어떤 방식으로 가져올 수 있는지 아래만 판단합니다.

1. 공식 공개 API로 어디까지 가능한가
2. map.naver.com 웹 크롤링/스크래핑을 운영 수집 경로로 써도 되는가
3. 현재 MVP에서 추천할 데이터 확보 전략은 무엇인가

## 직접 답변

- 공식 공개 API 기준으로 확인되는 플레이스 관련 기능은 `지역 검색`과 `주소/좌표 변환` 중심입니다.
- 현재 공개 문서 기준으로 `지역 검색 결과 1건의 상세 플레이스 정보를 다시 조회하는 공식 place-detail API`는 확인되지 않았습니다.
- 네이버 API 이용약관은 `네이버 지역정보를 수집하여 별도 데이터베이스로 관리하며 이용하는 행위`를 금지 예시로 명시합니다.
- 네이버 서비스 이용약관은 사전 허락 없는 자동화 수단(봇, 스파이더, 스크래퍼 등)으로 검색·수집·우회 행위를 시도하지 말라고 명시합니다.
- 네이버의 검색결과 수집 정책은 네이버 데이터베이스가 robots.txt 등으로 보호되며, 이를 무시한 수집은 저작권/정보통신망법 문제로 이어질 수 있다고 안내합니다.
- `map.naver.com/robots.txt`는 일반 User-agent에 대해 `Disallow: /`를 반환합니다.

## 공식 문서 근거

### 1) 지역 검색 API는 `후보 검색 결과` API다

출처:
- https://developers.naver.com/docs/serviceapi/search/local/local.md

확인 내용:
- 지역 검색은 `네이버 지역 서비스에 등록된 업체 및 기관을 검색한 결과`를 반환합니다.
- 요청 URL은 `https://openapi.naver.com/v1/search/local.json` 입니다.
- 하루 호출 한도는 `25,000회`입니다.
- 응답 필드 문서에 `item/link`는 `업체, 기관의 상세 정보 URL`로 설명되지만, 예시 응답은 빈 값입니다.
- `item/telephone`는 `값을 반환하지 않는 요소`라고 명시되어 있습니다.

판단:
- 공식적으로 보장되는 것은 `검색 결과 목록`입니다.
- 상세 JSON 재조회용 공개 엔드포인트는 이 문서에서 이어지지 않습니다.

### 2) 공식 Maps API는 주소/좌표/경로 중심이다

출처:
- https://api.ncloud-docs.com/docs/en/ainaverapi-maps-overview
- https://navermaps.github.io/maps.js.en/docs/naver.maps.Service.html

확인 내용:
- Maps overview는 공식 REST API 목록으로 `Static Map`, `Directions 5`, `Directions 15`, `Geocoding`, `Reverse Geocoding`를 안내합니다.
- 같은 문서는 Maps 기능을 `static map image generation`, `route navigation`, `address search`, `address conversion`으로 설명합니다.
- NAVER Maps JS API v3의 `naver.maps.Service` 문서는 `geocode`와 `reverseGeocode` 계열을 설명합니다.

판단:
- 현재 공개 문서에 보이는 공식 Maps 계열 기능은 `상세 플레이스 조회`보다 `지도/경로/주소 변환` 쪽입니다.
- 공개 문서만 기준으로 하면 `place id -> 상세 플레이스 JSON` 같은 안정 계약은 확인되지 않습니다.

### 3) API 약관은 네이버 지역정보의 별도 DB화에 매우 보수적이다

출처:
- https://developers.naver.com/products/terms/
- https://developers.naver.com/notice/article/21979

확인 내용:
- NAVER API 서비스 이용약관은 `네이버 지역정보를 수집하여 별도 데이터베이스로 관리하며 이용하는 행위`를 금지 예시로 듭니다.
- 같은 약관은 `기타 각 API의 제공 취지나 목적에 맞지 않게 API 제공 정보를 저장하거나 이용하는 행위`도 금지 예시로 둡니다.
- 2025년 5월 27일 시행 공지는 사전 승인 없는 자동화 수단(스크립트, 매크로, 봇, 크롤러 등)으로 API 서비스 또는 시스템에 주기적/반복적으로 접속하거나 명령을 전달하는 행위를 더 명확히 금지한다고 설명합니다.
- 같은 공지는 위반 시 `API 호출 차단`, `클라이언트 아이디 회수`, `API 이용계약 해지`, `민형사상 조치` 가능성을 안내합니다.

판단:
- `지역 검색 API로 후보를 긁어와 내부 식당 DB를 계속 쌓는 구조`는 현재 약관 문구와 긴장도가 높습니다.
- 이 부분은 `기술 가능`보다 `약관 적합성`이 먼저 검토되어야 합니다.

### 4) 서비스 약관은 웹 크롤링/스크래핑을 더 직접적으로 제한한다

출처:
- https://policy.naver.com/policy/service.html
- https://policy.naver.com/policy/search_policy.html

확인 내용:
- 네이버 서비스 이용약관(현재 페이지 기준 시행일 2025-07-10)은 사전 허락 없이 자동화 수단(매크로, 로봇, 스파이더, 스크래퍼 등)으로 로그인, 게시물 게재, 회원 ID/게시물 수집, 특정 질의어 검색/클릭, 기술적 조치 우회 등을 시도하지 말라고 안내합니다.
- 검색결과 수집 정책은 네이버가 네이버 서비스로 구축되는 데이터베이스를 `robots.txt` 등의 보호 장치로 보호한다고 설명합니다.
- 같은 정책은 robots.txt로 보호된 네이버 데이터베이스를 타 검색 로봇이 수집하는 것을 불허한다고 설명합니다.
- 같은 정책은 이를 무시한 수집이 경우에 따라 `저작권 침해` 또는 `정보통신망 이용촉진 및 정보보호에 관한 법률` 위반이 될 수 있다고 안내합니다.

판단:
- map.naver.com HTML 스크래핑, 무인 브라우저 반복 접근, 내부 XHR 재생성은 정책 리스크가 높습니다.
- `개인 실험`과 `서비스 운영용 지속 수집`은 위험도가 다르지만, MVP 서비스의 기본 수집 경로로 채택하기에는 방어가 어렵습니다.

## 소스 레퍼런스 근거

### map.naver.com robots.txt

출처:
- https://map.naver.com/robots.txt

확인 내용:
- `User-agent: *`에 대해 `Disallow: /`
- 예외 허용은 `/` 루트와 `/p/` 등 매우 제한적 경로만 보입니다.

판단:
- 최소한 현재 시점의 robots 정책은 `일반 크롤러의 광범위 수집을 허용하는 상태`가 아닙니다.
- 이것은 약관 자체를 대체하지는 않지만, 운영 크롤링에 부정적인 추가 신호입니다.

## 리스크 정리

### 공식 API 사용

- 리스크 수준: 중간 이상
- 이유:
  - 상세 플레이스 API 부재
  - 약관상 `지역정보 별도 DB화` 금지 예시 존재
  - API 호출 차단/키 회수 가능성 존재

### 웹 크롤링 / Playwright / Selenium

- 리스크 수준: 높음
- 이유:
  - 서비스 약관의 자동화 수단 제한
  - 검색결과 수집 정책과 robots 충돌
  - anti-bot 대응 가능성
  - 프런트 내부 API 스키마 드리프트
  - 운영 중 장애 재현성과 유지비용 큼

### 내부 API 직접 호출 재현

- 리스크 수준: 매우 높음
- 이유:
  - 비공개 계약
  - 사전 공지 없는 필드/인증 변경 가능
  - 차단되면 대체 경로 없음

## 추천 결론

### 추천하지 않는 것

- `네이버 웹 크롤링`을 콜키지 서비스의 주 수집 파이프라인으로 설계
- `지역 검색 API -> 내부 식당 DB 영구 저장`을 약관 확인 없이 기본 전략으로 채택
- `map.naver.com` 내부 요청을 재현해 상세 정보를 지속 수집

### 추천하는 것

1. 네이버는 `운영 참고/수동 검수 보조` 정도로만 취급
2. MVP 기본 데이터는 아래 중 하나로 전환
   - 운영자 수동 입력
   - 식당 제보
   - 파트너/허가된 제3자 데이터
   - 별도 라이선스가 명확한 장소 데이터
3. 콜키지 정보는 반드시 `자체 검증 데이터`로 분리
4. 네이버 데이터를 계속 쓰고 싶다면, 저장 범위와 사용 방식에 대해 `네이버 측 확인 또는 법률 검토`를 먼저 진행

## MVP용 실무 권고안

- 1단계: 네이버 의존 없는 `자체 식당 DB 스키마` 먼저 확정
- 2단계: 콜키지 정보는 운영자 검수/사용자 제보 기반으로 수집
- 3단계: 네이버는 식당 탐색 참고 화면 또는 운영 조사 툴 수준에서만 검토
- 4단계: 서비스 공개 전 `약관 적합성 체크리스트` 별도 작성

## 최종 판단

`현재 시점(2026-05-18) 기준으로 네이버 웹 크롤링은 corkage 프로젝트의 권장 수집 전략이 아닙니다.`

가장 안전한 방향은:

- 네이버를 핵심 DB 소스로 보지 않고,
- 콜키지 정보는 자체 데이터로 구축하며,
- 네이버 사용 여부는 `약관 적합한 범위의 제한적 보조 수단`으로만 다시 검토하는 것입니다.
