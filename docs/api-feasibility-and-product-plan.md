# API Feasibility and Product Plan

## 목표

네이버 지도 또는 네이버 API를 사용해서 `콜키지 가능한 식당`을 보여주는 웹 서비스의 MVP 가능성을 먼저 판단합니다.

현재 질문은 `어떻게 구현할까`가 아니라 아래입니다.

1. 네이버 쪽 API만으로 어디까지 가능한가
2. 콜키지 데이터는 어디서 확보할 것인가
3. MVP를 어떤 범위로 잘라야 하는가

## 0. 2026-05-18 재확인 결과

이번 재확인에서 중요한 제한이 더 명확해졌습니다.

- 네이버 API 서비스 이용약관은 `2025년 5월 27일 개정` 기준으로, 네이버 지역정보를 수집해 `별도 데이터베이스로 관리하며 이용하는 행위`를 금지하고 있습니다.
- 같은 약관은 회사의 사전 승인 없이 `스크립트, 매크로, 봇, 크롤러` 등 자동화 수단으로 주기적/반복적으로 접근하는 행위를 금지하고 있습니다.
- 네이버 개발자 FAQ에는 `검색결과를 보여주는 서비스` 또는 `네이버와 유사한 검색서비스`의 경우 오픈 API 검색결과를 상업적 목적으로 사용할 수 없다고 안내되어 있습니다.
- `map.naver.com/robots.txt`는 현재 크롤링을 허용하지 않는 방향으로 열려 있습니다.
- 2026-04-16 공지와 2026-06-25 18:00 KST 종료 공지는 Web Dynamic Map(JS v3), Static Map, Geocoding, Reverse Geocoding 범위를 함께 봐야 합니다.
- 공지 본문은 현재 확인되지 않아, 종료 범위는 공지 메타와 공식 문서 교차 확인 수준으로만 기록합니다.
- 이 때문에 지도/지오코딩 레이어는 `네이버 Maps 계열 유지`가 아니라 `standalone Maps 대체 경로`를 먼저 검토해야 합니다.
- 2026-05-18 라이브 확인에서는 지역 검색 API의 `telephone`가 계속 비어 있었고, `link`는 비어 있거나 외부 URL/Naver URL이 섞여 있었습니다.
- 같은 라이브 확인에서 `display=10` 요청은 `display=5`로, `start=2` 요청은 `start=1`로 사실상 보정되었습니다.

즉, 현재 시점에서는 `네이버 API나 네이버 크롤링을 식당 후보 영속 저장의 주 데이터 소스`로 잡는 방향 자체가 위험합니다.

## 1. 현재 확인된 API 가능성

공식 문서 기준으로 확인된 내용:

### 가능한 것

- standalone Maps 기준으로 웹 지도 표시
- standalone Maps 기준으로 지도 위 마커/오버레이 표시
- Geocoding API로 주소 -> 좌표 변환
- Reverse Geocoding API 계열로 좌표 -> 주소 변환
- 지역 검색 API로 식당/업체 후보 검색
- 지역 검색 결과에서 `title`, `category`, `description`, `address`, `roadAddress`, `mapx`, `mapy`, `link` 같은 기본 필드 확인

### 바로 안 풀리는 것

- `콜키지 가능 여부` 자체를 공식 API 필드로 바로 받는 구조는 확인되지 않음
- 즉, 식당 검색과 콜키지 여부는 별도 데이터 문제로 분리해야 함
- 지역 검색 결과 뒤에 붙는 `공식 상세 정보 조회 API`는 현재 공식 문서에서 확인되지 않음
- 지역 검색 응답의 `telephone` 필드는 공식 문서상 `값을 반환하지 않는 요소`로 안내됨
- 지역 검색 응답의 `link`는 `업체, 기관의 상세 정보 URL`로 설명되지만, 예시 응답에서는 비어 있어 안정적인 상세 데이터 연동 포인트로 보기 어려움
- Web Dynamic Map(JS v3), Static Map, Geocoding, Reverse Geocoding는 종료 공지 이후 네이버 Maps 계열 전제에서 분리해 다뤄야 함

## 1-1. 지역 검색 후 상세 정보 조회 가능 여부

현재 공식 문서 기준 결론은 아래와 같습니다.

- `검색 결과 목록 조회`는 가능
- `결과 1건의 상세 정보를 JSON API로 추가 조회`하는 공식 엔드포인트는 확인되지 않음
- 따라서 `지역 검색 -> place id 획득 -> 상세 API 재조회` 같은 구조는 공식 공개 API 기준으로는 어렵다고 보는 편이 안전함

즉, 네이버 공식 공개 API만 기준으로 하면 지역 검색 뒤에 받을 수 있는 정보는 사실상 `검색 결과에 포함된 필드 범위` 안에서 판단해야 합니다.

## 2. 핵심 판단

가장 중요한 결론은 이것입니다.

`네이버 지도는 지도/위치 표현용 후보일 수 있지만, 네이버 검색 결과를 제품용 식당 DB의 기반으로 삼는 방향은 현재 약관/정책 기준으로 위험하다.`

이 결론은 아래 두 가지를 합친 판단입니다.

- 공식 문서에서 지도, 지오코딩, 지역 검색은 확인되지만 `콜키지 가능 여부` 전용 데이터 필드는 확인되지 않음
- 현재 약관/FAQ/robots 기준으로는 `네이버 검색 결과 수집 -> 자체 DB화 -> 서비스 노출` 경로가 안전한 기본 전략으로 보기 어려움

## 3. 따라서 현실적인 MVP 구조

### MVP A. 수동 큐레이션형

가장 현실적인 첫 버전입니다.

- 지도는 네이버 지도 사용
- 식당 기본 정보는 `수동 입력` 또는 `약관상 저장/표시가 명확히 허용되는 별도 소스` 사용
- 네이버 검색은 운영자 참고용 수동 확인 정도로만 제한적으로 검토
- 콜키지 가능 여부는 직접 조사 후 저장
- 운영자가 식당을 등록/수정

장점:

- 가장 빨리 시작 가능
- 데이터 품질을 통제 가능

단점:

- 확장 속도가 느림
- 운영 수작업이 필요함

### MVP B. 반수동 수집형

- 지역 검색으로 후보 식당을 먼저 모음
- 이후 수동 검수로 콜키지 여부만 채움
- 내부 DB에서 최종 공개

주의:

- 현재 네이버 약관/FAQ 기준으로는 이 방식을 `그대로` 제품 기본 수집 전략으로 쓰기 어렵습니다.
- 제휴나 별도 승인 없이 진행하는 기본안으로는 추천하지 않습니다.

장점:

- 초기 등록 속도가 더 빠름
- 지도 UX와 데이터 축적을 같이 시작 가능

단점:

- 검수 프로세스 설계가 필요함

### MVP C. 사용자 제보형

- 일반 사용자나 운영자가 콜키지 가능 식당 제보
- 검수 후 공개

장점:

- 확장성이 좋음

단점:

- 허위 정보와 최신성 관리 이슈가 큼

## 4. 추천 방향

현재 단계 추천은 `MVP A + 비네이버 데이터 소스 검증` 입니다.

이유:

- 현재 약관/정책 리스크를 가장 작게 가져갈 수 있음
- 가장 중요한 `콜키지 가능 여부`와 `저장/공개 가능한 식당 기본 정보`를 같은 기준으로 관리할 수 있음
- 이후에 네이버를 붙이더라도 `지도 표현 레이어`와 `데이터 저장 레이어`를 분리한 채 검토할 수 있음

## 5. 먼저 테스트할 API 항목

### 테스트 1. 지도 렌더링 가능 여부

확인할 것:

- standalone Maps로 웹에서 지도 로딩이 안정적인가
- standalone Maps에서 마커 수십 개 정도까지 UX가 괜찮은가
- 모바일 브라우저에서도 무난한가

성공 기준:

- 서울 특정 구역 기준으로 지도 표시 가능
- 샘플 마커 표시 가능
- 기본 확대/이동/선택 UX 확인 가능

### 테스트 2. 지역 검색으로 식당 후보 확보 가능 여부

확인할 것:

- `와인바`, `레스토랑`, `이탈리안`, `스테이크`, `콜키지` 같은 검색어 조합이 얼마나 쓸만한가
- 검색 결과의 품질이 MVP 후보 수집에 충분한가
- 검색 결과만으로 상세 페이지 없이도 후보 선별이 가능한가
- 약관상 `저장`, `재배포`, `상업적 사용` 경계가 어디까지인지 분리해서 기록할 수 있는가

성공 기준:

- 특정 지역에서 후보 식당 리스트의 품질은 파악 가능
- 이름/주소/카테고리/좌표 정도의 필드 특성은 파악 가능
- 단, 이 결과를 `영속 저장 가능한 제품 DB 소스`로 봐도 되는지는 별도 정책 검토 결과와 함께 판단

### 테스트 3. 주소-좌표 변환 정확도

확인할 것:

- standalone Maps + Geocoding/Reverse Geocoding 조합으로 검색 API 결과 주소를 지도 좌표로 안정적으로 연결 가능한가
- 중복 매장/지점 처리 방식이 필요한가

성공 기준:

- 후보 식당을 지도에 안정적으로 표시 가능

### 테스트 4. 콜키지 데이터 입력 구조

확인할 것:

- 콜키지 가능/불가/확인중 상태가 필요한가
- 병당 비용, 잔당 비용, 와인잔 가능 여부, 콜키지 프리 조건 등 세부 필드가 필요한가

성공 기준:

- 내부 데이터 스키마 초안 작성 가능

## 6. API 테스트 결과 문서화 형식

각 테스트는 아래 형식으로 남기는 것이 좋습니다.

- API 이름
- 문서 링크
- 약관/운영정책 링크
- 인증 방식
- 브라우저 직접 호출 가능 여부
- 서버 프록시 필요 여부
- 얻을 수 있는 필드
- 영속 저장 가능 여부
- 상업적 사용 경계
- MVP에 필요한지 여부
- 제한 사항
- 샘플 응답 여부
- 최종 판단: 사용 / 보류 / 제외

## 7. 제품 기획에서 먼저 정해야 할 것

### 사용자 가치

- 사용자는 무엇을 가장 빨리 알고 싶나
- `콜키지 가능 여부`가 핵심인지, `콜키지 비용/조건`까지가 핵심인지

### 검색 범위

- 서울만 할지
- 수도권까지 할지
- 전국으로 열어둘지

### 데이터 신뢰도 표기

- `확인 방식`과 `최신성`을 함께 보여주는 방식으로 정하는 편이 안전합니다.
- 최소 표시는 아래 4개 축으로 고정하는 편이 좋습니다.
  - 직접 확인
  - 사용자 제보 검수 완료
  - 오래된 정보
  - 확인 필요

### 사용자 제보 처리 규칙

- 사용자 제보는 `즉시 공개`하지 않고 항상 `검수 대기` 상태로 먼저 저장
- 제보에는 최소한 `제보 내용`, `제보일`, `근거 메모`를 남김
- 기존 공개 정보와 충돌하는 제보는 `기존 값 즉시 덮어쓰기` 대신 `재확인 필요`로 내려서 운영자 검수 큐로 보냄
- 운영자 확인 또는 매장 재확인 전까지는 `콜키지 가능/불가` 최종 상태로 승격하지 않음
- 공개 상세 화면에는 `사용자 제보 기반`인지 `직접 확인`인지 출처를 분리해서 표시

### 최신성/신뢰도 라벨 규칙

- 최신성은 `마지막 확인일` 기준으로 계산
- 권장 표기 예시
  - 최근 확인: 30일 이내
  - 확인 필요: 31일~90일
  - 오래된 정보: 91일 이상 또는 날짜 불명
- 신뢰도는 출처와 최신성을 같이 반영
  - 높음: 직접 확인 또는 매장 확인 + 최근 확인
  - 중간: 사용자 제보 검수 완료 + 확인일 존재
  - 낮음: 오래된 정보, 상충 제보 존재, 또는 재확인 미완료
- `오래된 정보`와 `확인 필요`는 숨기지 말고 그대로 노출하는 편이 신뢰에 유리함

### 사용자 신뢰 고지 문구

- 목록/상세 공통 고지 예시:
  - `콜키지 정책은 방문 전 매장에 다시 확인하세요.`
  - `마지막 확인일과 확인 방식을 함께 확인하세요.`
  - `사용자 제보만 있는 정보는 운영자 재확인 전까지 달라질 수 있습니다.`
- `오래된 정보` 또는 `확인 필요` 상태일 때는 위 고지를 기본 문구보다 더 눈에 띄게 보여주는 편이 좋습니다

### 상세 정보 범위

후보 필드:

- 식당명
- 주소
- 좌표
- 전화번호
- 카테고리
- 콜키지 가능 여부
- 콜키지 비용
- 병 수 제한
- 와인/위스키 등 주종 제한
- 잔 세팅 가능 여부
- 최신 확인일
- 확인 방식
- 신뢰도 라벨
- 제보 상태
- 출처 메모

## 8. 지금 시점의 에이전트 운영 추천

1. `researcher`
   - 공식 문서 확인

5. `verifier`
   - 실제 테스트 결과가 가설과 맞는지 검증

6. `writer`
   - 의사결정 문서 고정
