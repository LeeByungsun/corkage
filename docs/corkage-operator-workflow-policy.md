# Corkage Operator Workflow Addendum

작성일: 2026-05-18

이 문서는 `콜키지 데이터 정책`의 보조 섹션 초안입니다.

범위는 4가지입니다.

- 사용자 제보 접수
- 정본 레코드 갱신 규칙
- 오래된 정보 처리
- 관리자 검수 단계

중요한 전제는 아래입니다.

- 네이버 검색/크롤링 결과는 `운영 참고용 후보 정보`일 수는 있어도 `공개용 정본 콜키지 정보`를 자동으로 만들면 안 됩니다.
- 공개 화면은 항상 `검수된 정본 레코드`만 읽어야 합니다.
- 사용자 제보는 중요 입력이지만 `도착 즉시 공개`나 `도착 즉시 덮어쓰기`를 하면 안 됩니다.

## 1. 운영 객체를 분리합니다

최소한 아래 4개를 분리해서 생각하는 편이 안전합니다.

### 1) 후보 식당 정보

- 이름
- 주소
- 좌표
- 카테고리
- 후보 수집 출처

이 객체는 `발견용`입니다.

아직 검수되지 않은 콜키지 사실을 담는 정본이 아닙니다.

### 2) 정본 콜키지 레코드

공개 상세 페이지가 읽는 단일 기준값입니다.

예시 필드:

- corkageStatus
- corkageFee
- bottleLimit
- alcoholTypeLimit
- conditionNote
- verifiedAt
- sourceType
- sourceNote
- confidenceLabel

### 3) 사용자 제보

제보 1건은 `원본 이벤트`로 남깁니다.

예시 필드:

- 제보 시각
- 제보자 식별값 또는 연락 가능 수단
- 식당 식별 정보
- 주장한 콜키지 상태
- 주장한 비용/조건
- 근거 설명
- 근거 날짜
- 첨부 증빙 여부

### 4) 검수 로그

관리자가 무엇을 보고 어떤 판단을 했는지 남깁니다.

예시 필드:

- reviewer
- reviewedAt
- decision
- decisionReason
- changedFields
- followUpNeeded

## 2. 사용자 제보 접수 규칙

사용자 제보는 많이 받을수록 좋지만, 입력 순간의 신뢰도는 낮게 가정하는 편이 안전합니다.

### 필수 입력

최소 아래는 받아야 합니다.

- 식당명
- 주소 또는 지도상 식별 정보
- 콜키지 가능/불가/모름 중 하나
- 제보 근거의 날짜
- 근거 설명

### 선택 입력

- 병당 비용
- 프리 조건
- 병 수 제한
- 주종 제한
- 잔 세팅 가능 여부
- 영수증/메뉴판/문자/통화 메모 같은 증빙

### 접수 시 즉시 적용 규칙

- 제보 원문은 수정하지 않고 저장합니다.
- 동일 식당의 기존 정본 레코드는 접수만으로 바꾸지 않습니다.
- 증빙이 없는 제보도 받을 수는 있지만 기본값은 `낮은 신뢰도`입니다.
- 같은 식당 제보가 여러 건 들어오면 원본은 각각 유지하고, 검수 큐에서만 묶습니다.

## 3. 관리자 검수 상태와 공개 상태를 분리합니다

`제보 검수 상태`와 `공개용 corkageStatus`는 다른 값이어야 합니다.

### 제보 검수 상태 예시

- 검토대기
- 검토중
- 추가확인필요
- 승인
- 반려

### 공개용 corkageStatus 예시

- 가능
- 불가
- 확인중
- 정보오래됨

운영상 중요한 규칙은 아래입니다.

- `승인된 제보`만 정본 레코드 갱신 후보가 됩니다.
- `추가확인필요`는 공개값을 바꾸지 않고 후속 확인 작업을 만듭니다.
- `반려`는 내부 로그만 남기고 공개 데이터에는 영향이 없어야 합니다.

## 4. 정본 레코드 갱신 규칙

정본 레코드는 `가장 최근 제보`가 아니라 `가장 최근에 검수 통과한 사실`이어야 합니다.

### 갱신 전 확인 항목

- 식당 식별이 정확한가
- 제보 날짜가 명확한가
- 비용과 조건이 특정 날짜/이벤트 한정인지 구분됐는가
- 기존 정본과 충돌하는가
- 변경하려는 필드마다 근거가 충분한가

### 갱신 규칙

- 공개 페이지는 항상 정본 레코드만 읽습니다.
- 승인 제보가 와도 모든 필드를 한 번에 덮어쓰지 않습니다.
- `상태`와 `비용/조건`은 따로 갱신할 수 있어야 합니다.
- 상태 근거는 충분하지만 비용이 불명확하면 `corkageStatus`만 갱신하고 `corkageFee`는 유지 또는 비웁니다.
- `verifiedAt`는 검수 완료 시각이 아니라 `사실이 확인된 날짜`를 우선 사용합니다.
- `sourceType`은 승인된 근거 중 가장 강한 출처를 남깁니다.

### 충돌 규칙

새 제보가 기존 정본과 충돌하면 보수적으로 처리합니다.

- 핵심 사실이 충돌하면 공개 상태를 바로 확정하지 말고 `확인중`으로 내립니다.
- 오래된 비용/조건이 새 제보와 충돌하면 구조화 필드는 숨기거나 비우고, 내부 확인 후 다시 공개합니다.
- 충돌 제보가 들어온 순간 후속 확인 작업을 생성합니다.

## 5. 오래된 정보 처리 규칙

콜키지 정보는 수시로 바뀔 수 있으므로 `삭제`보다 `노후 표기`가 안전합니다.

기본 초안은 아래처럼 둘 수 있습니다.

- `0~90일`: 일반 표시
- `91~180일`: 경고 배지 또는 주의 문구 표시
- `181일 이상`: `정보오래됨`으로 전환

이 숫자는 운영 데이터를 본 뒤 조정할 수 있지만, 초기에는 보수적인 기본값이 필요합니다.

### 자동 처리 규칙

- `verifiedAt`가 180일을 넘기면 자동 삭제하지 않고 `정보오래됨`으로 내립니다.
- 오래된 데이터는 마지막 확인일과 함께 보여줍니다.
- 오래된 상태에서는 비용/조건을 보여주더라도 `현재와 다를 수 있음` 경고를 같이 붙입니다.
- 충돌 제보가 새로 들어오면 남은 유효기간과 무관하게 즉시 재검토 대상으로 올립니다.

### 재검증 우선순위

아래는 먼저 다시 확인합니다.

- 트래픽이 많은 식당
- 최근 충돌 제보가 있는 식당
- 콜키지 프리 조건처럼 이벤트성 변동이 잦은 식당
- 비용/조건이 복잡한 식당

## 6. 관리자 검수 단계

권장 흐름은 아래입니다.

1. 식당 식별
   - 같은 지점인지 확인
   - 중복 후보가 있으면 병합 기준 결정

2. 제보 근거 확인
   - 날짜가 있는지 확인
   - 실제 통화/방문/증빙인지 확인
   - 단순 추정인지 확인

3. 기존 정본과 비교
   - 상태 충돌 여부 확인
   - 비용/조건 충돌 여부 확인
   - 최근 검증일 확인

4. 결정
   - 승인
   - 추가확인필요
   - 반려

5. 정본 반영
   - 바꾼 필드만 반영
   - verifiedAt, sourceType, confidenceLabel 갱신
   - 내부 검수 로그 저장

6. 후속 작업 생성
   - 매장 재확인 필요 여부 기록
   - 오래된 정보 재검증 일정 기록
   - 반복 충돌 식당 주시 목록 등록

## 7. 공개 규칙으로 연결되는 운영 원칙

- 미검수 제보는 공개하지 않습니다.
- `사용자 제보`만으로 공개하더라도 마지막 확인일과 신뢰도 라벨을 같이 보여줍니다.
- `웹 공개 정보 참고`만으로는 비용/조건을 강하게 확정하지 않습니다.
- 운영 메모와 반려 사유는 내부 전용으로 두고 공개하지 않습니다.
- 네이버 후보 데이터는 식당 탐색 보조에만 쓰고, `검증된 콜키지 사실`처럼 보이게 섞지 않습니다.

## 8. 메인 정책 문서에 붙일 핵심 bullets

메인 정책 문서에 최소 아래는 들어가야 합니다.

- 제보 검수 상태와 공개 상태를 분리한다.
- 사용자 제보는 원본 이벤트로 저장하고 즉시 공개하지 않는다.
- 정본 레코드는 승인된 사실만 필드 단위로 갱신한다.
- 충돌 제보가 오면 보수적으로 `확인중` 또는 비공개 처리한다.
- 오래된 정보는 삭제보다 `정보오래됨` 표기를 우선한다.
- 마지막 확인일, 출처, 신뢰도 라벨을 공개 규칙에 포함한다.
